# Tora playable authoring

Use Tora's existing project service and validated authoring operations. The user's creative request supplies the concept; this skill supplies the workflow and discovery entry point.

## Load current requirements and capabilities

With connected Tora MCP tools, call `tora_brief` at the start of the task. Read the returned production brief, playable brief, win and CTA guidance, and authoring documentation in full. On re-reads or after context compaction, pass `alreadyRead: [{ name, sha256 }]` using the returned `digests` so unchanged briefs are omitted while any updated file is returned in full. Discover supported contracts cheaply with `tora_capabilities({ summary: true })` followed by `tora_capabilities({ packs: [...], format: "compact" })` (which preserves every range, enum, default, and unit in compact form). Do not invent endpoints or operations.

Without MCP, locate the Tora checkout and read `PRODUCTION_MASTER.md`, the workspace's required playable brief, and `docs/TORA_CREATION_API.md`. Use the configured editor origin; the documented local default is `http://127.0.0.1:8001`. Start the documented local editor if needed and available, then query `GET /api/creation/capabilities`. If the checkout, required brief, or connection is unavailable, identify the missing setup instead of silently authoring without it. Setup instructions live in `docs/TORA_AGENT_SETUP.md` in the checkout.

## Produce a coherent playable

Apply the [win effects and CTA guidance](references/win-effects-and-cta.md) and [Tora UI fundamentals](../tora-ui-fundamentals/SKILL.md) on the first generation. Read them here when working locally and use the same documents returned by `tora_brief` when connected.

Establish one visual style and a brief asset plan before scene construction. Source all production artwork and audio from free third-party libraries such as Kenney, Flaticon, or another source with a verified license that permits the intended commercial use. Use one coherent visual pack or style family per playable, including characters, environments, props, puzzle items, UI, and effects. Audio may come from a separate compatible sound pack. Record the source URL, author, license identifier and text, required attribution, original file path, and downloaded file hash for each asset. Verify attribution and redistribution obligations before packaging.

Prepare sourced files through faithful cropping, resizing, transparent-padding removal, or supported format conversion when needed. Preserve the original download and its license evidence. Asset creation through image generation, custom illustration, procedural drawing, or synthesized audio is outside this authoring workflow. Keep useful object/layer editability and separate interaction geometry. Build compositions from the sourced objects and inspect them at the target phone size. Existing demonstration games illustrate API usage and require their own source and style review before reuse.

Prove one representative scene at the intended phone size before expanding the ad. Include responsive motion, suitable sound, and clear visual rewards. Follow the current briefs' acceptance gates, including packaged screenshots and footage. Compilation and export cannot establish visual quality.

## Author and inspect safely

Create a new project or inspect the requested existing project. Use `tora_inspect({ id, tree: true })` for a compact scene outline before targeted `ids` reads (`full: true` only when you truly need the complete JSON document); preserve unrelated objects and scenes. Use `tora_list_assets` and `tora_fetch_cc0_pack` to discover/cache verified CC0 packs and `tora_stage_cc0_assets` to stage them with server-enforced provenance and single-visual-style-family validation. When sprite sheets or padded sprites need faithful mechanical preparation (`crop`, `trim`, `resize`/`maxSide`, or `sliceGrid`), run `tora_prep_assets` and upload the emitted `.tora/prepared-assets/...` paths via `tora_upload_assets` (which verifies the hash-bound prep manifest and preserves provenance and `styleFamily`). For raw studio assets, use `tora_upload_assets` with workspace `filePath` items (up to 32 files in one atomic revision, avoiding the 12 MiB MCP frame limit), or `tora_upload_asset` for a single file. Raw PNG/JPEG/WAV/MP3 uploads up to 8 MiB are optimized automatically while original masters are retained; use `optimize:"lossless"|"none"`, `preserveResolution`, workspace `filePath`, or an original `sourceHash` when needed. Connect delivered assets to image components through the supported operations.

Submit edits through `tora_edit`, with the inspected `expected` revision and intended changed record IDs in `scope`. Use `scopeCreates: true` to auto-allow brand-new records without duplicating every new ID in `scope` — any pre-existing component, behavior, event, binding, or variable referenced by a new record (or `$project.base`) still requires explicit inclusion in `scope`. A `PREVIEW` response is not a committed change: inspect the effects and either adjust scope and commit the cached preview directly via `commitPreviewDigest` (without re-emitting `operations[]`) when those effects belong to the requested task, or revise your operations. On a stale revision, inspect again before rebuilding the edit. Never blindly replay edits or bypass validation. For HTTP authoring, use the documented preview/commit sequence and revision checks.

Use `tora_qa` to run static, acoustic, four-viewport, primary-interaction, and motion-filmstrip verification. During mid-build iteration passes, inspect `screenshots/contact-sheet.png` and `screenshots/filmstrip-interaction.png` (plus `screenshots/filmstrip-end-card.png` and opt-in `recordVideo: true` → `screenshots/gameplay.webm`) to verify layout, animation progression, and reward effects, **then inspect the individual full-size viewport PNGs and real interactive playback before final delivery** — contact sheets and headless filmstrips are triage helpers only and do not satisfy display-size or physical-device inspection. Use `tora_render` for scene preview and `tora_export` for the packaged playable, including batch multi-network delivery with `tora_export({ id, targets: [...], outputDir })`. Discover all seven network target IDs through `tora_capabilities`; Google Ads, Mintegral, and TikTok return deterministic ZIP artifacts, while Unity, AppLovin, Meta, and ironSource return single HTML. Rendering writes an artifact; actually open and inspect it using available browser or image tools. Review motion, gameplay, transitions, and the end card in the exported playable, repair defects, and recheck affected behavior.

Deliver both an editable project bundle and the playable artifact, with paths or links and concise verification evidence. Distinguish engineering checks, AI visual inspection, user approval, real-device testing, and official network acceptance. Current standalone browser drafts are not network-qualified exports. Configure a real destination when supplied; do not claim campaign readiness with an example store URL.
